Concevoir le système d’information d’une école qui grandit

Une école rurale de trois classes gérait ses élèves, ses notes et ses emplois du temps dans des documents séparés. En cinq semaines, notre équipe a conçu sa base de données avec MERISE, l’a fait évoluer pour accueillir les spécialités, puis a montré comment l’IA peut aider la direction à repérer les élèves en difficulté.

    Le besoin

    Une école qui veut quitter le papier sans se bloquer pour la suite

    L’établissement voulait un outil centralisé, inspiré de PRONOTE, pour gérer les élèves, les enseignants, les classes, les matières, les salles et les emplois du temps. Il devait aussi suivre l’école dans ses évolutions, à commencer par l’ouverture de spécialités en première.

    « Comment mettre en place un système de gestion scolaire adapté à une école en pleine évolution, pour centraliser ses informations, simplifier son organisation et mieux gérer les emplois du temps et les spécialités ? »

    Ce que les enquêtes ont appris

    Partir des usages réels, pas d’un modèle idéal

    Un noyau commun de cinq modules

    Emploi du temps, évaluations et bulletins, vie scolaire, cahier de textes, communication avec les familles. La paie reste hors périmètre.

    Les spécialités se gèrent par groupes

    Comme dans PRONOTE, un cours n’est plus rattaché à une classe entière mais à un groupe d’élèves, qui peut mélanger plusieurs classes.

    Deux faiblesses de PRONOTE à corriger

    À l’ISJA, les changements de salle se font à la main et rien n’empêche le sureffectif. Notre base compare la capacité de la salle à l’effectif avant chaque affectation.

    Un rythme adapté au monde rural

    Créneaux fixes de deux heures, mercredi après-midi libre, longue pause de midi pour les élèves éloignés, samedi matin réservé aux devoirs surveillés.

    Formes normales vérifiées

    • 1FN

      Chaque donnée est atomique : un seul téléphone par professeur, une seule adresse par élève, et les horaires vivent dans CRÉNEAU, pas dans une liste.

    • 2FN

      Rien ne dépend d’une partie seulement d’une clé : dans ÉVALUER, la note dépend de l’élève, du cours et de la date ensemble.

    • 3FN

      Aucune donnée non clé ne dépend d’une autre : le professeur et la matière d’une note se retrouvent par le cours.

    Modéliser avec MERISE

    Le cours au centre, et trois actions plutôt que trois objets

    Avant de dessiner, nous avons écrit les règles de gestion et recensé chaque donnée. Le modèle vérifie les trois formes normales et ne stocke rien en double : une moyenne ou un effectif se calcule, il ne s’enregistre pas.

    34
    règles de gestion, chacune traduite en contrainte ou en déclencheur
    46
    données dans le dictionnaire, avec type et contraintes
    3FN
    vérifiée pour toutes les tables
    12
    tables obtenues avec 6 règles de passage au MLD
    1. 1
      Une note est une action

      Une note n’existe pas seule : c’est un élève évalué dans un cours, à une date. Elle devient l’association ÉVALUER. Même logique pour l’absence, S’ABSENTER.

    2. 2
      Le cours, pivot du système

      Il réunit une matière, un professeur et un groupe d’élèves. Tout ce qui se passe à l’école se rattache à un cours.

    3. 3
      L’emploi du temps est une association à trois

      PLANIFIER relie un cours, une salle et un créneau. Une contrainte d’intégrité fonctionnelle garantit qu’un cours, sur un créneau donné, n’a qu’une seule salle.

    4. 4
      Le groupe, ajouté pour les spécialités

      Chaque classe a son groupe de tronc commun ; un élève s’inscrit en plus dans deux spécialités au maximum.

    Créer et tester

    Un script SQL qui refuse les erreurs avant qu’elles n’arrivent

    Le modèle est traduit en script MySQL, avec une version adaptée à SQLite Cloud pour l’exécuter en ligne. Les règles qu’une clé ou un CHECK ne peut pas exprimer sont confiées à des déclencheurs.

    -- ÉVALUER : une note = un élève, un cours, une date
CREATE TABLE evaluer (
  id_eleve         INT          NOT NULL,
  id_cours         INT          NOT NULL,
  date_evaluation  DATE         NOT NULL,
  note             DECIMAL(4,2) NOT NULL,
  appreciation     VARCHAR(255) NULL,
  PRIMARY KEY (id_eleve, id_cours, date_evaluation),
  CHECK (note BETWEEN 0 AND 20),
  FOREIGN KEY (id_eleve) REFERENCES eleve (id_eleve),
  FOREIGN KEY (id_cours) REFERENCES cours (id_cours)
);

    Faire évoluer la base

    Momodou et Fatou : même classe, spécialités différentes

    Intégrer l’IA · preuve de concept

    Repérer tôt les élèves qui décrochent

    Parmi plusieurs usages comparés (emploi du temps automatique, aide aux appréciations, assistant pour les parents), nous avons retenu celui qui répond au besoin de la direction et qui s’appuie sur des données déjà présentes dans la base : notes, absences et retards.

    -- Alerte : 3 absences non justifiées ou plus,
-- ou une moyenne en baisse de 2 points entre deux périodes
WITH Notes AS (
  SELECT id_eleve, note,
         CASE WHEN date_evaluation < '2026-10-15' THEN 1 ELSE 2 END AS periode
  FROM evaluer),
CalculAbsences AS (
  SELECT id_eleve, COUNT(*) AS nb_absences
  FROM s_absenter
  WHERE type_absence = 'absence' AND justifiee = 0
  GROUP BY id_eleve),
NotesAnciennes AS (SELECT id_eleve, AVG(note) AS moyenne_t1
                   FROM Notes WHERE periode = 1 GROUP BY id_eleve),
NotesRecentes  AS (SELECT id_eleve, AVG(note) AS moyenne_t2
                   FROM Notes WHERE periode = 2 GROUP BY id_eleve)
SELECT e.id_eleve, e.nom, e.prenom,
       COALESCE(c.nb_absences, 0)             AS absences_non_justifiees,
       ROUND(nr.moyenne_t2 - na.moyenne_t1, 1) AS tendance
FROM eleve e
LEFT JOIN CalculAbsences c ON e.id_eleve = c.id_eleve
LEFT JOIN NotesAnciennes na ON e.id_eleve = na.id_eleve
LEFT JOIN NotesRecentes  nr ON e.id_eleve = nr.id_eleve
WHERE COALESCE(c.nb_absences, 0) >= 3
   OR COALESCE(nr.moyenne_t2 - na.moyenne_t1, 0) <= -2
ORDER BY absences_non_justifiees DESC, tendance ASC;

    Étape 1 : une requête d’alerte dans SQLite Cloud

    J’ai d’abord traduit le besoin en deux règles simples, écrites directement en SQL : signaler un élève qui cumule trois absences non justifiées, ou dont la moyenne baisse de deux points entre la première et la deuxième période.

    La période est calculée à partir de la date dans la requête, sans ajouter de colonne : la base reste sans donnée en double. Sur le jeu de test, la requête signale 7 élèves.

    Étape 2 : un score expliqué, en Python

    Une alerte oui/non ne dit pas qui voir en premier. Le script Python reprend ces signaux, ajoute la moyenne et les matières sous 10, et les combine en un score sur 100 qui explique chaque alerte.

    À rencontrerÀ surveillerPas d’alerte

    Score de risque sur 100, calculé sur le jeu de test (24 élèves fictifs, 296 notes). Survolez une barre pour voir les raisons de l’alerte.

    Règles du score, sur 100
    Moyenne générale basse (maximum à 8 ou moins)35
    Matières sous 10 (5 points par matière)15
    Baisse des notes plus forte que celle de la classe20
    Absences et retards non justifiés30
    3 absences non justifiées : rendez-vous immédiatalerte

    Une requête SQL calcule les indicateurs par élève, un script Python les transforme en score et explique chaque alerte. La baisse est comparée à celle de la classe : si un devoir était plus dur pour tous, ce n’est pas un signal individuel.

    Avec 24 élèves sur un trimestre, un modèle entraîné ne serait pas fiable. Les règles restent lisibles et vérifiables ; un modèle d’apprentissage deviendra possible après quelques années d’historique.

    Précautions

    • Qualité des données : une absence mal saisie fausse le score.
    • Confidentialité : les élèves sont mineurs ; seuls les rôles autorisés de la table UTILISATEUR voient les alertes.
    • Fiabilité : le score déclenche une alerte, pas un jugement. La décision reste humaine.
